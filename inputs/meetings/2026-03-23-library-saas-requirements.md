## まとめ

大学図書館向け SaaS ウェブアプリケーション（司書向け管理システム ＋ 利用者向け OPAC）の機能要件、ターゲット戦略、差別化の方向性を検討した。

### SaaS アプリケーションの目的と構成

- 司書向けの業務フロー管理システムと、学生・一般利用者向け OPAC を、**同一データベースを参照する2コンポーネント**として構築。
- 契約大学のドメインを自動発行し、サイトのカラーテーマをカスタマイズ可能にする **マルチテナント SaaS** を目指す。

### ターゲット層とシステム機能

- 利用者層は **学生 / 教職員 / 一般** の3層。一般利用者登録は図書館での手続きでセキュリティを確保するのが最善。
- 既存サービスとの差別化として **AI 活用 / Google カレンダー連携 / 国立国会図書館 API による ISBN 自動登録** を検討。

### OPAC と管理者機能

- OPAC: 検索・予約・在庫確認・配送依頼・貸出期間延長など、モバイル利用前提のユースケース。
- 管理: 蔵書管理・利用者管理・貸出返却管理に加え、延滞管理・各種お知らせの作成/編集。

## 詳細

- **SaaS の概要**: 全国の大学図書館司書が契約に基づき、貸出・返却・本の登録・ユーザー管理・期限延長などの業務フローを行うシステム。学生証やバーコードをスキャンして貸出を完了する機能を含む。
- **利用者向け OPAC**: 一般利用者・学生がスマホ/PC で利用する Web サイト。ログインして貸出状況（借りている冊数等）の確認や本の予約ができる。
- **構成と展開**: 管理画面と OPAC の2コンポーネントが同一 DB を参照。契約完了時に図書館のドメイン（例 `library.ac.jp`）を自動発行し、複数大学が同じシステム/OPAC を展開できる構想。
- **ターゲットと差別化**: まず既存システム未導入の大学から開始、将来は既存システムからの移行も視野。差別化は大学ごとのカラーテーマ/プライマリカラーの展開。
- **SaaS 化のメリット**: 複数大学のデータを一元蓄積し活用（例: 著名大学の教授/学生が読む本のデータを共有 → 他大学の蔵書導入計画に活用、著名人のおすすめ本リスト等で独自性を高める）。
- **付加機能**: AI 活用、Google カレンダー連携（返却日の自動設定・通知、予約順番が回ってきた際の通知）。
- **利用者層とアカウント管理**: 学生 / 教職員（教員・事務員）/ 一般 の3層。学生・教職員は固有 ID（学籍番号・従業員 ID）で突合。一般はバーコード付き図書カードのユニーク番号で一元管理し、登録時のセキュリティを確保。
- **一般利用者の登録手続き**: 電子化（DX）は望ましいが、誰でも登録できるのを防ぐため、図書館に来館して登録するのがセキュリティ面で最も高い。
- **利用者側ユースケース**: 検索 / 予約 / 予約待ち人数の確認 / 複数キャンパス・拠点間の在庫確認・表示 / 別キャンパスへの配送依頼・受取設定 / お気に入り / 貸出履歴 / 現在の貸出状況（返却期限含む）/ 貸出延長（例 2週間）。主にスマホ利用を想定。
- **管理者側ユースケース**: PC で管理。利用者一覧・蔵書一覧の確認、蔵書詳細（ISBN・保管場所・登録日・貸出履歴）の確認。書籍の新規登録・情報編集・削除、OPAC お知らせ（おすすめ本・閉館時間変更等）の作成・編集。
- **書籍情報の取得**: 登録時の職員負担軽減のため、ISBN スキャンで書名・著者・ページ数などの書誌を自動取込。国立国会図書館 API を利用。
- **カスタマイズ性**: 大学ごとにプライマリカラー/色指定（カラーコード・ピッカー）を UI で設定。管理画面の主要機能はユーザー管理・本管理・返却貸出管理・お知らせ・延滞管理・トップの概要表示（在庫数・貸出中冊数）。
