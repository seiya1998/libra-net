# サーバーパフォーマンスルール

OPAC 検索など利用者向けレスポンスの速度はサーバーのクエリ効率に直結する。早すぎる最適化はしないが、以下は既定の規律とする。

## DB / クエリ（infrastructure・リポジトリ層）

- **YOU MUST**: N+1 を避ける（join / バッチ取得で集約。ループ内クエリ禁止）。
- **YOU MUST**: 必要なカラムだけ select する（過剰取得しない）。
- **YOU MUST**: 一覧はページネーション（カーソル推奨）。**NEVER** 全件取得。
- **YOU MUST**: マルチテナント前提で **`tenant_id` を複合インデックスの先頭**に置く（全クエリがテナントscope）。キャンパス別在庫/可用性は `(tenant_id, campus_id, ...)`。検索・絞り込みキーにもインデックスを用意（Drizzle スキーマ／マイグレーションで定義）。
- **YOU MUST**: 蔵書検索は **PostgreSQL の全文検索（`tsvector` / `pg_trgm` ＋ GIN インデックス）**を使う（`integrations.md` の `SearchPort` 実装）。`LIKE '%...%'` の全表走査を避ける。
- 巨大テーブルは将来 `tenant_id`／期間でのパーティショニング、さらに **Citus（`tenant_id` シャーディング）** を検討（ADR-002）。
- トランザクションは必要な範囲に限定（長時間保持しない）。
- **YOU MUST**: 適切な**インデックス設計・テーブル設計**を行う（`db.md`）。重いクエリは **`EXPLAIN`（実行計画）を確認**し、フルスキャン・filesort・一時テーブルを避ける（想定したインデックスが使われているか検証）。

## レスポンス / シリアライズ（presentation 層）

- **YOU MUST**: レスポンス JSON Schema を定義し、Fastify の高速シリアライズ（fast-json-stringify）を効かせる（`schema.md` と整合）。
- 大きなレスポンスはページング／ストリーミングで返す。

## キャッシュ

- 変化の少ない参照は適切な無効化とセットでキャッシュする（キャッシュ基盤は Redis 等が候補。非同期基盤の runtime 決定と合わせて選定）。

## イベントループ

- **NEVER**: リクエスト経路で同期的な重い処理（CPU バウンド）をブロッキング実行しない。非同期 I/O を使い、重い処理は分離する。

## 計測

- 最適化は計測（クエリ時間・p95 レイテンシ）に基づいて行う。
