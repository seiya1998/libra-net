# 意思決定記録 (ADR)

重要な技術・設計判断を記録する。

## ADR-001: サーバーアーキテクチャ

- **状態**: 採用
- **文脈**: `@libriori/server`（Fastify + Drizzle）のアーキテクチャと、ORM 乗り換えやテスト容易性への耐性が必要。
- **決定**:
  - **オニオンアーキテクチャ**（`domain` / `application` / `infrastructure` / `presentation`）＋ **リポジトリパターン**を採用。
  - ビジネスロジックは **domain に置く（リッチドメイン）**。`application` は薄いユースケース層。
  - Web 層は **Railway Oriented Programming**（`ramda` の `pipe` + `ts-pattern` の `match.exhaustive`）。
  - API 型は **OpenAPI**（JSON Schema → `@fastify/swagger` 生成 → admin が Aspida で取込）。
- **結果**: ORM（Drizzle）依存が `infrastructure` 層に隔離され、`domain` / `application` を ORM・Fastify 非依存で単体テストできる。規約は `.claude/rules/server/`。

## ADR-002: マルチテナント分離

- **状態**: 採用（改訂: DB を PostgreSQL に変更・Pool＋RLS）
- **文脈**: 契約大学ごとの SaaS。**複数大学データの横断活用が差別化の核**（EP-006: 教授おすすめ・人気本 等）。一方で**物理分離を求める強セキュリティ大学**も想定。テナントは少数・大口（数十〜数百校、各 数百万〜数千万行）。
- **決定**:
  - **DB = PostgreSQL**（MySQL から変更）。理由は **RLS（行レベルセキュリティ）** と **Citus（テナント・シャーディング）**。
  - 分離モデルは **Pool（共有スキーマ＋行レベル `tenant_id`）を既定**（横断分析を最優先）。
  - 分離は**多層防御**: ①リポジトリのチョークポイントで `tenant_id` 強制注入 ②型で TenantContext 必須化 ③**RLS で DB レベル強制**（`FORCE ROW LEVEL SECURITY`・非 owner ロール接続・`SET LOCAL app.current_tenant` をトランザクション内設定）④分離テスト。
  - テナント識別は**サブドメイン**（`{univ}.libriori.com`）→ 解決した `tenant_id` を全層と RLS セッション変数へ。
  - **横断分析は明示的な専用 read-only パス**（集計ロール）。**匿名・集計値のみ・大学ごとオプトイン（同意）**、非提供の大学は対象外（Q-021）。
  - **強セキュリティ大学は Hybrid で Silo（専用 DB/インスタンス）に切り出す**（物理分離＝横断分析対象外）。リポジトリのチョークポイントを「テナント→接続先」差し替え可能に設計し、必要時に切り出す（最初から作り込まない）。
- **結果**: 横断分析がタダ・運用が軽い・PG 接続モデルと整合。分離は RLS＋アプリ層の二重で担保。物理分離要求には Hybrid で個別対応。
- **スケール**: テナントscope クエリは `tenant_id` 先頭の複合インデックスで総行数非依存。巨大化は **パーティション（`tenant_id`/期間）→ リードレプリカ → Citus（`create_distributed_table` で `tenant_id` 分散・巨大テナント隔離）**。規約 `multi-tenancy.md` / `security.md`（`.claude` 規約も PostgreSQL / Pool＋RLS に更新済み）。

## ADR-003: 外部連携・検索の腐敗防止層

- **状態**: 採用
- **文脈**: NDL / NACSIS-CAT（CiNii Books）/ Google Calendar / AI / 検索を扱う。外部の不確実性を domain に持ち込みたくない。
- **決定**: domain にポート、infrastructure にアダプタ。外部モデルは境界で domain モデルへ変換。timeout/retry/フォールバック。
- **結果**: 外部依存が infrastructure 1層に隔離。検索は将来エンジン差し替え可。**書誌取得元も差し替え可**（初期 NDL → 国立大学向けに NACSIS-CAT / CiNii を追加。EP-013）（規約 `integrations.md`）。

## ADR-005: 検索基盤

- **状態**: 採用（初期）
- **文脈**: OPAC 蔵書検索。
- **決定**: **PostgreSQL の全文検索（`tsvector` / `pg_trgm`）** で開始。検索を domain の `SearchPort` で抽象化。
- **結果**: 初期はシンプル、将来 Meilisearch/OpenSearch 等へアダプタ差し替えで移行可。

## ADR-006: 非同期処理基盤

- **状態**: 保留（入口の抽象化は採用、ランタイムは未決）
- **文脈**: 返却通知・予約順番・延滞検出・NDL同期・カレンダー連携。
- **決定**: 非同期は HTTP と別入口から application ユースケースを実行（冪等・リトライ）。**ランタイム（ワーカー＋キュー / Lambda・バッチ）は未決**。application/domain はランタイム非依存。
- **結果**: ランタイム選定を後回しにしても手戻りなし（規約 `async-jobs.md`）。

## ADR-007: 認証方式

- **状態**: 採用（改訂）
- **文脈**: 学生 / 教職員 / 一般の3層。マルチテナント（大学ごと）。大学は統合認証 / 学認（SSO）を持つことが多いが、SaaS 横断での SSO 連携は運用が重い。自前でのパスワード保管は避けたい。
- **決定**:
  - 認証は **外部マネージド IdP（AWS Cognito / Auth0 等）に委譲**。**自前 DB にパスワードを保存しない**（DB は利用者プロフィール＋IdP のユーザー参照のみ）。認証は **port-adapter で抽象化**（ADR-003 と同方針）。
  - ログイン識別子は **種別の番号（学籍番号 / 従業員ID / 図書カード番号）＋ パスワード**（メールはログインに使わない。メールは連絡先＝通知・復旧用に保持）。**SNS ログインは無し**。
  - **当面は ID＋パスワード**。**将来、テナント（大学）ごとの SSO（学認 / SAML / OIDC）フェデレーション**を IdP 経由で追加できる設計とする（今は実装しない）。
  - 学外（一般）は図書館発行 ID（図書カード番号）＋パスワード。
  - **多要素・アクセス制御（面ごとに分ける）**: OPAC（利用者）は **MFA 必須**（方式はメール OTP 推奨 / SMS / TOTP から選定。Q-014）。管理画面（スタッフ）は **MFA なし＋許可 IP 制御**（図書館ネットワーク等の固定 IP からのみ。テナントごとに許可 IP 設定。Q-015）。いずれも認証は外部 IdP（Cognito 等）に委譲。
- **結果**: 認証情報の保管責任を IdP に移譲（漏洩リスク低減）。将来の大学別 SSO を塞がない。ベンダー・ユーザープール戦略は infra / 設計で確定（`questions.md`）。規約 `security.md`。

## ADR-008: API エンドポイント分離

- **状態**: 採用
- **文脈**: 管理画面（PC・書き込み多）と OPAC（モバイル・公開・読み多）。
- **決定**: 共有 domain/application/infrastructure の上に、presentation を **admin API / opac API の2面**。`@fastify/autoload` を surface ごとに register し、**管理画面＝`/admin/*`、OPAC＝root（`/*`、例 `/books`）**でマウント。認可/ミドルウェアは surface 単位でカプセル化。OPAC を root に置くのは「公開 API を主・admin を namespace」の慣用に沿う。
- **結果**: アクセス特性に応じた認可/キャッシュ最適化を分離可能。register 分割は起動時のみで実行時ルーティング性能に影響なし（規約 `architecture.md`）。

## ADR-009: イミュータブルデータモデリング

- **状態**: 採用
- **文脈**: 図書館は貸出・返却・予約など「起きた事実」が中心。状態の上書きより、履歴・監査・事実からの導出を重視したい。
- **決定**: テーブルを **リソース（`R_`）** と **イベント（`E_`）** に分類。**イベントは `created_at`（発生日時）のみ・append-only・不変**（更新/削除しない、`updated_at` 不使用）。状態（貸出中・在庫・延滞・予約待ち）はイベントから導出。リソースは `updated_at` を使わない。テーブル命名は `R_` / `E_` プレフィックス。
- **現在状態の射影 `current_status`**: 読み取り（一覧・検索・在庫表示）の性能のため、リソースに **`current_status`（現在の状態）列を持つことを許容**する。**関連イベントの追記と同一トランザクションで更新**し、**イベントから再構築可能**に保つ（真実はイベント側、`current_status` はその射影＝読み取りモデル）。例: 所蔵 `current_status`（整理中 / 在架 / 貸出中 / 予約取置 / 配送中 / 返送中 / 紛失 / 破損 / 除籍）、利用者 `current_status`（有効 / 停止 / 失効）。
- **結果**: 履歴が自然に残り監査可能。ROP / 関数型の不変性とも整合。状態参照は `current_status` で高速・真実はイベントで担保（規約 `db.md`）。

## ADR-010: 蔵書モデル（書誌 / 所蔵の分離）

- **状態**: 採用
- **文脈**: 蔵書管理（EP-001）。同一タイトルの複数所蔵、バーコードによる貸出（US-007）、紛失・破損など所蔵単位の状態管理、キャンパス別在庫（EP-005）が必要。
- **決定**: 蔵書を **書誌（Bibliography）** と **所蔵（Copy）** に分離する。
  - **書誌** = 作品/版の情報（タイトル・著者・出版社・出版年・ページ数・ISBN・分類(NDC)・書影 等）。**ISBN でテナント内一意**。
  - **所蔵** = 書誌に紐づく物理的な1冊。**バーコード（テナント内一意）**・所属キャンパス・配架場所（請求記号）・状態（`整理中` / `在架` / `貸出中` / `予約取置` / `配送中` / `返送中` / `紛失` / `破損` / `除籍`。`発注中` は EP-010 発注で追加）を持つ。
  - 在庫・可用性は所蔵の集計で表す（(書誌, キャンパス) 単位）。貸出・予約・配送は**所蔵単位**。
  - 図書館の概念モデル FRBR の Item、一般的な ILS（Koha 等）に倣う。
- **結果**: 貸出・予約・在庫・キャンパスを所蔵単位で自然に表現できる。除籍は状態で表し物理削除しない（ADR-009 と整合）。要件は EP-001（requirements / spec）。

## ADR-011: 監査ログ（改竄不可・追記型）

- **状態**: 採用
- **文脈**: 個人情報・貸出履歴を扱う SaaS。停止・督促一括・代理操作・テナント設定変更など重要操作の説明責任が要る（Figma A27 監査ログビューア由来）。
- **決定**: 管理操作を **改竄不可・追記型（append-only）の監査ログ**に記録する。記録項目: 操作者・ロール・操作種別・対象・日時・IP・重要度。**過去ログは編集・削除不可**（ADR-009 のイベント方針と同じ）。管理画面に**監査ログビューア**を設け、検索・フィルタで参照できる。停止・督促一括・代理モード・横断分析・個人情報参照・認証等は必ず記録。
- **結果**: 説明責任・不正検知・トラブル対応が可能。イミュータブル方針と一貫（規約 `security.md` / `db.md`）。
